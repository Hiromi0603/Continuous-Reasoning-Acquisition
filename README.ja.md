# Continuous Reasoning Acquisition

[English](./README.md) | [日本語](./README.ja.md)

**人が何をしたかだけでなく、なぜそうしたのかを、構造化され追跡可能なデータとして取得する。**

Continuous Reasoning Acquisition（CRA）は、AIアプリケーション、SaaS製品、社内ツール、研究システムに**推論データレイヤー（reasoning-data layer）**を追加するための参照アーキテクチャです。

CRAは、すでに次のようなイベント情報を取得できている一方で、その背後にある推論を取得できていないシステムを対象としています。

- ユーザーの行動  
- 会話  
- 業務ログ  
- CRMの記録  
- サポート対応のやり取り  
- 業務運用データ  
- 本人による報告

CRAは観測されたイベントから既知の情報を抽出し、不足している推論情報を検出します。必要に応じて不足部分を狙った追加質問を行い、その結果を追跡可能なReasoning Traceとして保存します。

```text
イベント / ログ / 会話
        ↓
初期抽出（Initial Extraction）
        ↓
推論情報の欠落検出（Gap Detection）
        ↓
対象を絞った追加質問（Adaptive Elicitation）
        ↓
構造化されたReasoning Trace
        ↓
時系列の推論データセット
```

## CRAで構築できるもの

CRAは、次のようなシステムに推論情報の取得機能を追加するために利用できます。

- CRM / セールスイネーブルメントツール  
- AIコーチングシステム  
- 従業員の振り返りツール  
- 専門家の知識を取得するシステム  
- 意思決定支援アプリケーション  
- カスタマーサポートプラットフォーム  
- 研修・教育製品  
- 人間とAIのインタラクションを扱うシステム  
- AIの評価・学習データパイプライン

例えば、次の情報だけを保存するのではなく、

```json
{
  "action": "discount offered",
  "outcome": "deal closed"
}
```

推論情報を扱うシステムでは、次のような情報を保持できます。

```json
{
  "event": "pricing negotiation",
  "observation": "customer repeatedly asked about implementation risk",
  "interpretation": "price was not the primary objection",
  "reason": "reduce perceived implementation risk before discussing price",
  "action": "shared migration plan before offering discount",
  "outcome": "deal closed",
  "sources": ["conversation_102", "followup_18"],
  "derivation": {
    "interpretation": "inferred",
    "reason": "extracted"
  },
  "verification": {
    "interpretation": "unconfirmed",
    "reason": "confirmed"
  }
}
```

ここで、**derivation**（導出）と**verification**（確認）は、互いに独立した軸を表します。

例えば、上記の解釈（interpretation）はシステムによって推論されたもので、まだ確認されていません。一方、理由（reason）は情報源から抽出され、その後、当事者本人によって確認されています。

目的は、単にLLMで説明文を生成することではありません。

**出所、変換過程、確認状態を追跡できる推論データを作成すること**が目的です。

## なぜLLMでログを要約するだけでは不十分なのか？

LLMはすでに、文章から説明を抽出できます。

より難しいのは、次の点を判断することです。

1. どの推論情報がすでに得られているのか  
2. 何がまだ不足しているのか  
3. 不足情報を推論によって補うべきか、質問して取得すべきか  
4. どの情報が当事者本人から直接得られ、どの情報がシステム由来なのか  
5. どの情報については質問による取得が一度も試みられていないのか  
6. 各Reasoning Unitがどのように生成されたのか  
7. 何が確認済みで、何が未確認なのか

数百件、数千件のイベントにわたって推論データを蓄積する場合、こうした区別はますます重要になります。

## ProvenanceとElicitation History

CRAは、次の違いを保持します。

```text
当事者本人が述べたこと
システムが抽出したこと
システムが推論したこと
後から確認されたこと
一度も質問されなかったこと
```

これが重要なのは、Reasoning Unitが存在しないことには、複数の意味があり得るためです。

```text
観測されていない（not observed）
≠
質問による取得を試みていない（not elicited）
≠
取得を試みたが未解決（elicitation attempted but unresolved）
```

例えば、意思決定基準が記録されていない理由としては、次の可能性があります。

- 元のイベント記録にその情報が含まれていなかった  
- Gap Detectionで追加質問の対象に選ばれなかった  
- システムが質問したものの、当事者本人が答えられなかった  
- 情報自体は存在していたが、最終的なスキーマに表現されなかった

Elicitation Historyを保持していなければ、後からこれらの状態を区別できなくなる可能性があります。

そのため、Elicitation Historyでは、次の情報を保持できます。

- 検出された欠落  
- 提示された質問  
- 取得対象の情報  
- 回答 / 無回答  
- 更新後の情報状態  
- 残っている欠落  
- 質問を終了した理由

前述の簡略化されたJSONは、概要を示すための例です。

Sources、Grounding、Derivation、Verification、Missingness、Elicitation Historyを含む完全な例は、次のファイルを参照してください。

## なぜ他の方法だけでは不十分なのか？

### ……すべてをJSONでログに記録すればよいのでは？

CRAの記録は、JSON、リレーショナルテーブル、グラフ構造、その他の保存形式で表現できます。

重要なのはシリアライズ形式ではありません。**システムが何をデータとして保持するか**です。

一般的なアプリケーションログでは、次の情報が保持されることがあります。

- 質問  
- 回答  
- モデルの出力

一方、次の情報まで保持されるとは限りません。

- どの推論情報の欠落が質問のきっかけになったのか  
- どの欠落について意図的に質問しなかったのか  
- 各Reasoning UnitをどのSourceが裏付けているのか  
- 各フィールドの情報が、本人の発言、抽出、推論のどれによるものなのか  
- 得られたReasoning Unitが確認されたかどうか  
- なぜ質問による取得を終了したのか

情報の取得時点でこれらの区別を記録していなければ、一部は後から信頼できる形で復元できません。

### ……W3C PROVを使えばよいのでは？

CRAはW3C PROVなどで定義される一般的なProvenance（来歴）概念と互換性があり、それらに対応付けることも可能です。

W3C PROVは、エンティティ、活動、エージェント、導出関係を表現するための汎用的な枠組みを提供します。

CRAは、Provenanceの概念を人間の推論データに特化して適用し、次のような領域固有の区別を定義します。

- 本人が述べた（subject-stated）/ システムが抽出した（system-extracted）/ システムが推論した（system-inferred）  
- 確認済み（confirmed）/ 未確認（unconfirmed）  
- 未観測（not observed）/ 未取得（not elicited）/ 未解決（unresolved）

目的はW3C PROVを置き換えることではありません。取得対象が人間の推論である場合に、どの来歴情報が重要なのかを具体化することです。

### ……LLMの可観測性ツールやトレーシングツールを使えばよいのでは？

LLMの可観測性ツールは、次のような問いに答えます。

- どのモデルが呼び出されたか  
- どのプロンプトが送信されたか  
- どの応答が返されたか  
- 呼び出しにどれだけ時間がかかったか  
- どのツールが呼び出されたか

CRAが扱うのは別のレイヤーです。

- その人は何を観測したのか  
- 何をどう解釈したのか  
- システムは何を推論したのか  
- その推論をどのSourceが裏付けているのか  
- その情報について本人に質問したことがあるのか  
- 得られたReasoning Unitは確認されたのか

LLMのトレーシングは、AIシステムが何をしたかを記録します。

CRAは、当事者の推論に関する情報がどのように取得、導出、確認されたかを記録します。

したがって、両者は二者択一ではなく、互いを補完する関係になり得ます。

## 主要コンポーネント

### Gap Detection

対象イベントについて、どの情報がまだ不足しているかを判定します。

代表的な欠落には、次のものがあります。

- 理由の欠落  
- 文脈の欠落  
- 解釈の欠落  
- 判断基準の欠落  
- 曖昧さ  
- 裏付けのない推論  
- 矛盾する情報

### Adaptive Elicitation

追加情報が必要な場合に限り、不足部分を狙った追加質問を生成します。

```text
既存データ
    ↓
不足している理由を検出
    ↓
質問：「BではなくAを選んだのはなぜですか？」
    ↓
イベントの状態を更新
    ↓
終了、または次の欠落を検出
```

### Reasoning Trace

一つのイベントに関連する推論を、生成された単一の要約文ではなく、構造化データとして保存します。

### Provenance

前述の[ProvenanceとElicitation History](#provenanceとelicitation-history)を参照してください。

### Longitudinal identity

Subject + Event + Timeの関係を保持し、後から複数のイベントにまたがる推論の分析を可能にします。

## アーキテクチャ

典型的な実装は、次のような構成になります。

```text
アプリケーション / SaaS / 社内システム
                │
                ▼
       イベント取得レイヤー
                │
                ▼
       推論情報取得レイヤー
        ├─ 抽出（extraction）
        ├─ 欠落検出（gap detection）
        ├─ 追加質問生成（follow-up generation）
        └─ 終了判定（stopping）
                │
                ▼
         Reasoning Data Layer
        ├─ Reasoning Units
        ├─ Sources
        ├─ Grounding
        ├─ Derivation
        ├─ Verification
        └─ Elicitation History
                │
                ▼
       アプリケーション別の活用
        ├─ コーチング
        ├─ 分析
        ├─ 知識移転
        ├─ パーソナライゼーション
        └─ AIの学習・評価
```

CRAは、特定のLLM、データベース、フロントエンド、推論の分類体系を前提としません。

## 責任ある利用

CRAは、人がどのように意思決定するかに関する情報を取得するため、通常の活動ログよりも機微性の高い情報を扱う可能性があります。

実装にあたっては、情報取得の目的を定義して当事者に説明し、適切な同意を得る必要があります。また、十分な設計上の検討なしに、推論データを個人の能力や業績を測る固定的な指標として利用することは避けるべきです。

本人が述べた情報とシステムが推論した情報の違いをユーザーが確認できるようにすることも、責任ある利用の一部です。
